# Proxmox → Proxmox Cold Copy Wizard

This workflow copies a **powered-off QEMU VM** between two independent Proxmox VE hosts without requiring the hosts to be members of the same cluster.

## Design goal

The operator does not need to type migration command parameters.

Start the ANSI interface:

\`\`\`bash
sudo lbm-vdrc
\`\`\`

Then select:

\`\`\`text
VM Migration
  └─ Proxmox → Proxmox Cold Copy (Independent Hosts)
\`\`\`

The wizard asks only for:

1. Source Proxmox IP/hostname
2. Source username
3. Source password
4. Source VM selected from live inventory
5. Destination Proxmox IP/hostname
6. Destination username
7. Destination password
8. Destination storage selected from live inventory
9. Destination VMID, with a safe default proposed automatically

The same wizard can also be started without parameters:

\`\`\`bash
sudo lbm-vdrc pve-copy
\`\`\`

## What the wizard reads automatically

From the source host:

- Proxmox version
- hostname
- QEMU VM inventory
- VM state
- VM CPU/RAM/disk metadata
- VM configuration
- source bridge names

From the destination host:

- Proxmox version
- hostname
- existing VMIDs
- next available VMID when required
- active storage targets that support VM images
- free/total storage information
- available Linux bridges

## Safety model

The source VM must already be **STOPPED**.

If it is running, the wizard refuses to continue. It does not automatically shut down the production VM.

The workflow is:

\`\`\`text
Source VM already OFF
        ↓
Preflight
        ↓
vzdump --mode stop --compress zstd
        ↓
Source SHA256
        ↓
Pull backup to LBM controller staging
        ↓
Controller SHA256 verification
        ↓
Push backup to destination Proxmox
        ↓
Destination SHA256 verification
        ↓
qmrestore to selected storage
        ↓
Destination VM remains OFF
        ↓
Bridge/network validation
        ↓
Operator review and manual start
\`\`\`

The source VM is never deleted.

The destination VM is never automatically started.

This avoids the risk of having the original and restored VM online at the same time with the same hostname, IP address or MAC address.

## Credentials

Passwords are requested with a hidden prompt and kept only in process memory.

The implementation uses:

\`\`\`text
sshpass -e
\`\`\`

so the password is supplied through the process environment rather than as a command-line argument.

Passwords are not written to:

- \`/etc/lbm-vdrc\`
- job history
- migration receipts
- command arguments generated by LBM-VDRC

For longer-term production automation, SSH keys remain preferable.

## Transfer path

The initial safe implementation uses the controller as a relay:

\`\`\`text
PVE01 → LBM controller → PVE02
\`\`\`

This is intentional. It avoids placing the destination password or trust material on the source host and works even when the two Proxmox systems have no direct trust relationship.

The controller therefore needs enough temporary free space for the generated \`.vma.zst\` backup.

Migration staging is stored under:

\`\`\`text
/var/lib/lbm-vdrc/migrations/
\`\`\`

A receipt containing non-secret migration details and SHA256 is written there after a successful copy.

## Required packages

On Debian/Ubuntu:

\`\`\`bash
sudo apt install -y openssh-client sshpass
\`\`\`

Or:

\`\`\`bash
sudo ./install.sh --install-deps
\`\`\`

Both Proxmox hosts must allow SSH for the supplied account and that account must have sufficient privileges to run:

- \`pvesh\`
- \`pvesm\`
- \`qm\`
- \`vzdump\`
- \`qmrestore\`
- \`sha256sum\`

For the initial implementation, \`root\` over SSH is the simplest supported path. Restrict SSH access at the network/firewall layer.

## Network validation

After restore, the wizard compares bridges referenced by the restored VM with bridges detected on the destination host.

If a bridge such as \`vmbr103\` does not exist on the destination, the copy still remains safely powered off and the wizard displays a warning.

Network mapping should be corrected before starting the restored VM.

## Rollback

Rollback is simple because the source VM is preserved.

If transfer, checksum verification or restore fails:

- the source VM remains untouched and powered off;
- the source \`vzdump\` backup is preserved;
- no automatic source deletion occurs;
- a partially created destination VM, if any, is left for explicit administrator review rather than being automatically destroyed.

To return service to the source host, verify that the destination copy is not running and manually start the original source VM.

## First production test

Use a non-critical VM first.

Validate:

- backup creation;
- both SHA256 checks;
- restore to the intended storage;
- target VM configuration;
- bridges/VLANs;
- BIOS/UEFI;
- EFI/TPM disks;
- passthrough devices;
- first isolated boot;
- guest services and networking.

Only after these checks should the workflow be used for a critical production VM.
